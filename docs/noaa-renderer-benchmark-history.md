## 2026-06-11 Vapor-Pressure LUT Experiment (Rejected)

- Tested under the relaxed rounding-error tolerance: a cubic-Hermite lookup table for the Bolton/Magnus saturation vapor pressure (1/16 C spacing, max relative error 1.7e-10) replacing the inline exp chain in the parcel segment integrator, moist ascent/descent integrators, and vaporPressureHpa. Microbenchmark showed 2.35x on isolated back-to-back evaluation.
- Interleaved same-run serial HRRR A/B showed the parcel core shrink only 4.75s -> 4.40s with total frame CPU flat (14.62s vs 14.68s): the real loops are instruction-throughput-bound, with out-of-order execution hiding exp latency behind surrounding arithmetic, while the LUT adds 2-4 cache-line loads per evaluation that compete with existing typed-array traffic. Reverted; isolated transcendental microbenchmarks do not transfer to these loops.
- Remaining frontier beyond the current dependency set and pure-JS implementation, with honest estimates: a faster deflate backend (zlib-ng; identical pixels, different artifact bytes; ~1.2-1.6s of the ~2.4s zlib share per dense frame; requires a native or WASM dependency), a WASM SIMD parcel kernel (~1.5-2.5s of the ~4.5s parcel core; large port plus dual-implementation parity burden), and GPU compute (largest possible win, largest lift). Within pure JS, current dependencies, and the established methodology, the measured floor stands. libdeflate landed 2026-06-11 (see "libdeflate PNG Backend (Landed)" below); no longer a candidate.

## 2026-06-11 Pure-JS Frontier Experiments (All Measured Null)

- Dry-adiabat pow factorization: hoisting midPressure^kappa per cell segment and reducing the per-(origin, dry-segment) lift to one multiply (ulp-level deviation) measured 11.78s vs 11.96s total on an interleaved same-run serial HRRR frame - the kernel lost 0.09s while segment prep gained the hoisted pows back. Convective origins sit mostly at or above their LCLs, so dry-lift pows are rare; the kernel cost is the saturated branch and plain arithmetic throughput. Reverted.
- zlib strategy on real artifacts: Z_RLE gzip of the 225MB HRRR hover payload ran 1195ms vs 840ms for the level-1 default and produced 62% larger output (40.0% vs 24.7% ratio); Z_HUFFMAN_ONLY was worse still. zlib level 1 already wins on this data; only a faster codec implementation (libdeflate-class) reduces this cost.
- Together with the vapor-pressure LUT null, these establish the measured pure-JS floor: per-frame worker CPU is bounded by methodology transcendental volume, plain arithmetic throughput, and zlib codec speed.

## 2026-07-14 Input Prefetch (renderer-input-prefetch; fetch/compute overlap for cold builds)

- Problem: cold builds alternate between network-bound waves (every frame worker in its fetch stage, CPU ~60%) and CPU-bound waves (all workers computing, network idle), because each worker runs fetch -> decode -> compute serially and frames dispatch in publication-ordered waves. Cold wall ~= fetch + compute instead of ~= max(fetch, compute). Measured on the 16-frame restore build: 1.43 GiB (1,463 MiB) downloaded, rangeFetch summed 170 s against ~135 s of decode+compute, largely serialized. The runtime's `prefetchFrameInput` hook existed for exactly this but NO caller ever injected it — it was dead code.
- Mechanism: `startFrameInputPrefetch` (scripts/lib/noaa-build/frame-queue.js) walks the queue-ordered main tasks (renderMode all/base — exactly one per frame) and warms the content-addressed selected-GRIB cache through the SAME `materializeSelectedGrib` entry the workers use (same locks, same tmp+rename publish, same post-publish verification), from the main process, concurrency 3 by default. The pump rotates past the initial dispatch wave (those frames' locks are already held by workers — prefetching them first would park every pump slot in a lock-wait) and circles back last, when they skip cheaply. A light readiness probe (content-addressed path + sidecar size match) keeps warm builds from re-hashing every file in the main process; the worker read path remains the authoritative verifier. Failures are swallowed and counted (`input prefetch: prefetched/skipped/failed` in the build log); `--input-prefetch=0|off` disables (default 3, clamp 0-8, unrecognized values warn and disable).
- Incident worth remembering: the first cut imported `CATALOG_VERSION` from the wrong module, silently got `undefined`, fell back to `materializeSelectedGrib`'s `"current-ui"` default token, and every prefetch landed at a cache path no worker ever reads — DOUBLING cold downloads while all unit tests passed (both unit-test calls agreed on the same wrong path). Only the cold A/B caught it (candidate slower everywhere; two `.grib2` files per hour differing only in version token). Fixed at the import, guarded by a module-load throw, and pinned by a test asserting the prefetch path lands in the worker namespace. Lesson: cross-module identifier imports fail as silent `undefined`; cache-namespace parity needs an explicit test against the CONSUMER's path.
- Cold A/B (baseline = parent commit worktree, per-model pinned 2026-07-14 runs, 4 render workers, selected-GRIB+idx caches deleted before every leg, ~110 MB/s network): single-wave legs (4 frames on 4 workers, zero lookahead room) neutral within noise — gfs 10/10 -> 9/10 s, nam 7/7 -> 7/8 s, nam3km 23/24 -> 23/26 s; HRRR 13 frames: 57/53 -> 50/53 s with 9/13 frames `raw=cache`. Deep queue (HRRR 12Z F000-F024, 25 frames, ~6 waves): 131/103 -> 88/96 s (mean -21%) with 18/25 frames prefetch-fed (`prefetched=24 skipped=1 failed=0`). Parity evidence comes from the 4-model cold A/B round (gfs+nam+nam3km 4 frames each + HRRR F000-F012): all 2,140 artifacts across those 25 frames byte-identical between the baseline and candidate cold builds of the same round.
- Bandwidth dependence (why the % is a floor, not a ceiling): on this fast network total fetch pipe-time (~13 s per 13-frame leg) is small against compute (~40 s), capping the possible win at ~15-25%. The win scales UP as the network slows — baseline wall ~= fetch + compute while overlapped wall ~= max(fetch, compute) — and the owner's home-network builds (long network-maxed stretches at ~60% CPU) are exactly the fetch-heavy regime where the overlap pays most. Full-build acceptance happens there. (A post-fix smoke of the same deep fixture landed at 398 s when the benchmark network degraded ~15x mid-session — per-frame fetch 4 s -> ~47 s even for worker-only wave-1 fetches — with wall ~= the pure network floor and compute fully hidden, i.e. the overlap behaving exactly as designed under a network-dominated regime.)

## 2026-07-15 Warm-First Dispatch + Wide Pump (renderer-input-prefetch; kill the fetch/compute alternation)

- Problem (owner-observed on a real full build, monitoring screenshot): CPU history showed repeated deep valleys between full-utilization plateaus while network alternated inversely — the classic wave pattern survived the first input-prefetch cut. Root cause is arithmetic: the pump ran 3 slots x 2 range connections while 18 workers consume 18 frames per wave, so the pump warmed ~3 frames per compute phase and the other ~15 workers still hit cold frames simultaneously, collapsing the pool back into a synchronized fetch wave (the 2026-07-14 hardening's politeness cap halved pump bandwidth and made this worse).
- Mechanism, two halves. (1) Wide pump: default 8 slots x 3 range connections (<= 24 upstream connections; flag/env clamp now 0-16 slots), sized so one wave's worth of frames warms during one compute phase. Not additive with the 72-connection worker budget in steady state because of (2) warm-first dispatch: `takeNextReadyTask` now takes a `taskPriority` hook — part tasks and dependency chains keep their natural order (priority 0), main frames whose selected GRIB the pump has warmed (or that are complete on disk) are preferred, and cold mains are deferred while preferred work exists. Deferred, never starved: with no preferred ready task the picker takes the first ready task, so a disabled pump degrades to exactly the old FIFO. Dependency gating (`canStartFrameTaskWithDependencies`) is still consulted for every candidate, so runmax-prefix and snow chains are order-safe by construction. Retries stay FIFO. Dispatch mix is observable in the `--profile` queue log as `dispatch=warm:X/cold:Y`.
- Cold A/B (HRRR 12Z F000-F048, 49 frames, default concurrency, baseline = 43f1a58 worktree, ABBA, 1 s CPU+RX sampler): wall 106/128 s -> 101/114 s (~-8% on a gigabit pipe with overnight drift inflating the later legs). ## Early Renderer Findings

- The largest remaining cold-render costs were renderer efficiency issues rather than source/website loading:
  - After the renderer hot-path pass, final default cold run averages were about `catalogPng=3.6s`, `synoptic=4.1s`, `hoverGrid=1.6s`, and `persist=7.4s` per frame.
  - NAM 3km high-hour accumulated precipitation remained expensive because source grids and composition can involve many APCP records.
  - Manifest persistence is now deferred by default for global full runs, but artifact writes still showed occasional multi-second spikes.
- Additional optimization findings:
  - Detailed synoptic vectors still render and persist, but detailed synoptic raster drawing is skipped when the simple raster is used for the PNG layer.
  - Detailed NOAA beta synoptic vectors now use a bounded contour grid instead of the full PNG raster grid. Simple and detailed vector payloads are still both generated/persisted; the cold profile dropped average `synoptic` time to about `0.32s/frame`.
  - Catalog scalar renders now use affine numeric transforms for common unit conversions instead of per-pixel JS callbacks, and step-color lookups use binary search.
  - Worker-to-main artifact transfer avoids an extra buffer copy when encoded artifacts already own their `ArrayBuffer`.
  - Frame artifact files now write directly while the per-frame completion marker and manifests remain atomic. The marker is removed before frame artifact persistence and restored only after all artifacts succeed, so interrupted forced renders are not treated as complete.

## Persist Queue And Concurrency Experiments

- Experimental decoupled persistence is available behind `--global-persist-queue`, but it is disabled by default after cold tests showed worse wall time and CPU utilization from write backpressure.
- Increasing persist concurrency/backlog to `16/96` was a failed experiment: it produced `real 309.99s` and much worse CPU utilization.
- A later decoupled persist retest with direct writes + bounded synoptic (`8/96`) was stopped early: render stayed busy, but persistence fell far behind (`persisted=9/83`, backlog `66/96`), implying a large final drain rather than a real wall-time win.
- Increasing `--global-frame-concurrency` to `96` was also stopped early: it kept workers busy but inflated per-frame materialize/decode costs and lagged the 48-slot run.
